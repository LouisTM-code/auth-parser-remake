# Введение: общие требования к модулю `ConfigLoader`

**Бизнес-цель.** Обеспечить единый точный вход в систему конфигурирования: прочитать манифест, детерминированно загрузить и провалидировать конфиги по JSON Schema, выполнить минимальные нормализации, спроецировать данные в строго типизированные DTO и вернуть итоговую модель результата для последующего запуска пайплайна. Ошибки на любом этапе — **fail-fast** с исчерпывающим сообщением.

**Техническая роль.** `ConfigLoader` — самостоятельный модуль без прямых зависимостей от прочих модулей пайплайна. Работает по этапам, описанным в рабочей спецификации пайплайна (чтение манифеста → поочерёдная обработка конфигов: чтение, sanity-check, JSON Schema-валидация, выбор профилей, семантические инварианты, интерполяция плейсхолдеров, пред-DTO нормализация, проекция в DTO, регистрация результатов → итоговая сборка результата).

## План работы модуля (верхнеуровневые требования)

### Область ответственности (Scope)

> Классы внутренней логики модуля содержат в начале `_` . Иначе это внешний API. В текущем модуле только класс `ConfigLoader` внешний.

#### `_ManifestReader`

* Чтение **манифеста v1** и валидация по схеме.
* Формирование DTO манифеста.
* Итерация по `configs[]` и запуск изолированной обработки каждого конфига (fail-fast при ошибке).

#### `_ErrorFormatter`

* спецификация требует структурированные ошибки с полями `code`, `message`, `config_id`, `type`, `profile_id?`, `json_pointer`.
* Сейчас у нас ошибки — просто исключения. Чтобы формировать отчёт строго по контракту, нужен класс-утилита, который преобразует исключения валидатора, Pydantic и собственные fail-fast проверки в единый формат.

#### Процесс обработки конфигов (многоуровневая система)

1. **`_ConfigReader`**  - Прочитать файл конфигурации и превратить его в валидный JSON-объект Python.

2. **`_ConfigSanityCheck`**  - Базовые проверки структуры: наличие `meta`, `profiles`, соответствие `config_id`, версиям и типу. 

3. **`_ConfigUniversalJsonSchemaValidation`**  - Валидация против схемы (Draft 2020-12), разрешение `$ref`. 

4. **`_ConfigActiveProfileSelector`** - управление активными профилями конфигов

5. **`_ConfigSemanticInvariantsByType`**  - Дополнительные правила по типам конфигов (например, уникальность `profile_id`, обязательные поля). 

6. **`_ConfigPlaceholderFilling`**  - Интерполяция плейсхолдеров `${env:*}`, `${secret:*}`. 

7. **`_ConfigNormalizerBeforeDTO`**  - Минимальная нормализация: применение `default`, канонизация enum-ов. 

8. **`_ConfigDTOProjector`**  - Строгая проекция в DTO через Pydantic v2 `TypeAdapter`. 

#### Внешний фасад — `ConfigLoader`

* Центральная точка вызова.
* Организует последовательное использование всех внутренних классов.
* Регистрирует результаты (DTO по типам, активные профили, версии).
* Возвращает итоговую структуру `ConfigLoadResult` для запуска пайплайна.

### Не-цели (Out of Scope)

* Кеширование (в релизе **не используется**).
* Бизнес-логика потребителей (компиляция regex, нормализация URL, проверка форматов за пределами схем и т.п.).
* Логирование «шиной» (LogBus) и интеграции — здесь только формирование детальных ошибок/результатов.

### Форм-фактор

**Описание:** Вместо дробления на отдельные модули, вся логика `ConfigLoader` реализуется в **одном файле**, но структурируется через набор **внутренних классов-подсистем**. Каждый класс инкапсулирует один этап пайплайна: чтение, проверки, нормализация, проекция в DTO.

**Цель:** Сохранить читаемость и модульность разработки, не нарушая требования «один исходный файл».

**Преимущества:**

* Чёткая изоляция логики по классам (тестируемые блоки).
* Проще сопровождать: каждая подсистема отвечает за один шаг.

**Тестирование:** Можно писать unit-тесты на каждый внутренний класс отдельно, а интеграционные — через фасад `ConfigLoader`.

Такой дизайн даёт **чистую архитектуру внутри одного файла**:

* внутренние классы скрывают детали шагов,
* внешний фасад даёт лаконичный API,
* тесты могут быть как «по шагам», так и сквозные.

### Вход/Выход (абстрактно)

* Вход: путь к манифесту (строка). Фактический контракт верхнего вызова зафиксируем на финальном этапе спецификации.
* Выход: объект-результат `ConfigLoadResult`, включающий:
  `manifest_dto`, `configs_by_type`, `active_profiles_by_type`, `schema_versions`, с финальной проверкой уникальности `config_id` среди успешно загруженных.

### Нефункциональные требования

**Надёжность и fail-fast**:

* Любая критическая ошибка на этапе чтения, валидации или проекции должна немедленно прерывать процесс загрузки, возвращая структурированную ошибку: `code`, `message`, `config_id`, `type`, `profile_id?`, `json_pointer`.
* Сообщения об ошибках — конкретные и воспроизводимые (чтобы чётко решать их либо на уровне схем, либо на уровне пред-DTO нормализации).

**Детеминизм**:

* Одинаковый вход ⇒ одинаковый результат (включая порядок обработки и выбора профилей).
* Выбор профилей строго по правилам: пустой `active_profiles` ⇒ первый профиль; иначе — только перечисленные `profile_id` в указанном порядке (ошибка, если `profile_id` отсутствует/дублируется).

**Производительность**:

* Обработка последовательная (без параллелизма) и без кеширования в текущем релизе.
* Изолированность по конфигам позволяет в будущем упростить распараллеливание без изменения контракта.

**Расширяемость и версионирование**:

* Поддержка новых типов конфигов достигается добавлением соответствующих JSON Schema и DTO без изменения ядра.
* Версии схем учитываются и отражаются в `schema_versions`.
* Семантические инварианты — расширяемый набор правил на этапе 2.5, без внедрения бизнес-логики потребителей.

**Трассируемость**:

* JSON Pointer до проблемного узла при проекции/валидации.

### Контракты ошибок (единый формат)

* Структура ошибки:
  `code` (enum/строковый код),
  `message` (чёткое объяснение),
  `config_id`, `type`, `profile_id?`, `json_pointer?`.
* Коды группируются по слоям: `MANIFEST_*`, `IO_*`, `SANITY_*`, `SCHEMA_*`, `SEMANTIC_*`, `INTERPOLATION_*`, `DTO_*`, `RESULT_*`. (Точное перечисление кодов зафиксируем в отдельном разделе спецификации ошибок `ConfigLoader`.)

### Проверяемость (DoD уровня спецификации)

* Принимаются **валидные** наборы конфигов: все этапы завершаются, формируется корректный `ConfigLoadResult`, согласованный со схемами и DTO.
* Для **каждого** слоя предусмотрены негативные тесты с fail-fast и структурированной диагностикой:
  манифест (нет файла/пустой/невалидный/дубликаты `config_id`), IO, sanity, schema, semantic, interpolation, DTO.
* Детерминированный выбор активных профилей (включая пустой список).

### Критические неопределённости и риски (для фиксации до реализации)

1. **Механизм secrets**: в текущем описании — только `st.secrets`. жёстко фиксируем Streamlit в этом релизе.
2. **Грани «где разрешено схемой» для интерполяции**: требуется перечисление полей по типам конфигов (чтобы интерполяция была предсказуемой и тестируемой).
3. **Полный список семантических инвариантов** по всем типам и версиям схем — зафиксировать как таблицу в спецификации (с тест-кейсам). Сейчас дано в «наброске», но требует формализации для стабильно-автоматических тестов.
4. **Коды ошибок**: требуется окончательная матрица кодов/примеров сообщений.
5. **Версионирование схем и миграции**: в этой версии миграций нет; если встретится несовпадение `expected_version`/фактической версии в файле — поведение строго fail-fast.

# Спецификации реализации по каждому классу

## A. `_ManifestReader`

### A-1. Цель класса

* **(Вызов):** Получить путь к манифесту, с которого начинается работа загрузчика конфигураций. Этот шаг фиксирует точку входа без уточнения финального формата входа/выхода (может измениться при интеграции с `PipelineLauncher`).
* **(Чтение манифеста и валидация):** Прочитать JSON-файл манифеста, проверить его корректность по `manifest.schema.json`, гарантировать, что список `configs` не пуст, и построить DTO `ConfigManifestV1` с вложенными `ManifestMeta` и `ConfigEntry`. Дополнительно выполнить fail-fast проверки: обязательные типы конфигов присутствуют и `config_id` уникальны.

### A-2. Библиотеки и технические подходы

1. **`pathlib` (stdlib)** – для безопасной работы с путями и проверки наличия файла.
2. **`json` (stdlib)** – десериализация содержимого манифеста.
3. **`jsonschema` (внешняя)** – валидация против схемы `manifest.schema.json` (Draft 2020-12).
4. **DTO-модуль `manifest_dto.py`** – строгая проекция данных в dataclass-структуры `ConfigManifestV1`, `ManifestMeta`, `ConfigEntry`.
5. **Fail-fast проверки** – ручные проверки бизнес-правил, которые не покрыты JSON Schema: наличие всех обязательных типов (`pipeline`, `network`, `site`, `url`, `auth`, `logging`, `export`) и уникальность `config_id`.

### A-3. Функциональные требования

1. Проверить, что файл существует и доступен для чтения (иначе `FileNotFoundError`).
2. Загрузить JSON и проверить корректность синтаксиса (`json.JSONDecodeError` → fail-fast).
3. Провалидировать содержимое по `manifest.schema.json`.
4. Убедиться, что `configs` не пустой массив.
5. Заполнить DTO `ConfigManifestV1` из данных манифеста.
6. Проверить бизнес-инварианты:
   * все необходимые `type` представлены хотя бы один раз;
   * `config_id` уникальны во всём списке.

### A-4. Нефункциональные требования

* **Fail-fast:** ошибка любого шага прерывает загрузку немедленно, исключение должно быть информативным (`code`, `message`, `config_id`, `type`, `profile_id?`, `json_pointer`).
* **Детерминизм:** одинаковый входной файл → одинаковый результат DTO.
* **Трассируемость:** при ошибке валидации сообщать JSON Pointer до проблемного узла.
* **Изолированность:** модуль не зависит от `PipelineLauncher` и других модулей пайплайна.
* **Расширяемость:** поддержка новых версий манифеста достигается добавлением схемы и DTO, без изменения ядра.

### A-5. Допущения и ограничения

* Поддерживается только версия `manifest.schema.json` v1.
* Кеширование результатов чтения и валидации **не используется** в текущем релизе.
* Пути внутри манифеста трактуются как относительные к корню проекта или абсолютные.
* Проверка корректности формата `expected_version` (SemVer) выполняется на уровне схемы, а интерпретация версий и миграций **не входит** в `_ManifestReader`.

### A-6. Критерии приёмки

1. **Позитивные кейсы:**
   
   * Корректный манифест читается, валидируется, DTO формируется успешно.
   * Все обязательные типы присутствуют, `config_id` уникальны.

2. **Негативные кейсы:**
   
   * Файл отсутствует → ошибка с кодом `IO_NOT_FOUND`.
   * Файл повреждён (невалидный JSON) → ошибка `IO_INVALID_JSON`.
   * Несоответствие схеме (отсутствует `manifest_meta.version`, `configs` пустой и т.п.) → ошибка `SCHEMA_VALIDATION_FAILED`.
   * Отсутствует один из обязательных типов конфигов → ошибка `SANITY_MISSING_TYPE`.
   * Дублирующиеся `config_id` → ошибка `SANITY_DUPLICATE_CONFIG_ID`.

3. **Условия успеха:**
   
   * DTO `ConfigManifestV1` корректно создан, содержит список `ConfigEntry` с валидными данными, готовыми для передачи на этап обработки конфигов.

## B. `_ConfigReader`. Разрешение пути и чтение

### B-1. Цель класса

Прочитать файл конфигурации, указанный в манифесте, и превратить его в валидный JSON-объект Python. На этом шаге фиксируется корректность доступа к файлу и его базовая структурная валидность до более сложных проверок.

### B-2. Библиотеки и технические подходы

* **`pathlib` (stdlib)** — удобное и кроссплатформенное управление путями, проверка существования и разрешение абсолютного пути.
* **`json` (stdlib)** — десериализация содержимого в Python-объекты.
* **Fail-fast исключения** — прерывание процесса при первой ошибке с кодом/сообщением.

### B-3. Функциональные требования

1. Разрешить путь:
   
   * если `path` относительный → трактовать относительно корня проекта `auth-parser-remake`;
   * если абсолютный → использовать как есть.

2. Проверить существование и доступность файла.

3. Открыть файл в кодировке UTF-8.

4. Прочитать и десериализовать JSON в Python-объект.

5. Fail-fast в случаях:
   
   * отсутствует файл или нет доступа к нему;
   * синтаксическая ошибка JSON;
   * результат пустой (`None`, `[]`, `""`) или не объект (`dict`).

### B-4. Нефункциональные требования

* **Fail-fast:** исключение должно останавливаться сразу, без попыток обработать другие конфиги.
* **Детерминизм:** одинаковый путь → одинаковый результат.
* **Трассируемость:** в сообщении ошибки указывать `config_id`, `type`, путь и причину.
* **Безопасность:** не загружать и не выполнять код, только чистый JSON.

### B-5. Допущения и ограничения

* Все конфиги формата v1 обязаны быть JSON-файлами в кодировке UTF-8.
* Символические ссылки и спец.файлы поддерживаются только если ОС позволяет их прочитать стандартным способом.
* Сжатые/бинарные форматы (например, `.json.gz`) **не поддерживаются**.

### B-6. Критерии приёмки

* Успешно возвращается объект `dict`, считанный из указанного файла.
* При отсутствии файла выбрасывается структурированная ошибка `IO_NOT_FOUND`.
* При невалидном JSON выбрасывается `IO_INVALID_JSON`.
* При пустом/необъектном документе выбрасывается `IO_INVALID_DOC`.

## C. `_ConfigSanityCheck`

### C-1. Цель класса

Выполнить минимальные структурные проверки конфигурации до «тяжёлой» JSON Schema-валидации. Это позволяет быстро выявить ошибки формата или несогласованность с манифестом и остановить обработку.

### C-2. Библиотеки и технические подходы

* **Базовые операции Python (`dict`/`list`)** — проверка наличия ключей и типов.
* **`enum.Enum` (ConfigType)** — проверка, что тип профиля входит в поддерживаемый набор.
* **Fail-fast исключения** — немедленный останов при нарушении инварианта.

### C-3. Функциональные требования

1. Проверить наличие ключей `meta` и `profiles`.

2. Убедиться, что:
   
   * `meta` — объект (`dict`),
   * `profiles` — массив (`list`).

3. Проверить согласованность с манифестом:
   
   * `meta.config_id == config_id` из `ConfigEntry`;
   * `meta.version` удовлетворяет `expected_version`.

4. Проверить, что `meta.pipeline_step` соответствует одному из значений `ConfigType(Enum)`.

### C-4.  Нефункциональные требования

* **Fail-fast:** ошибка одного конфига прерывает весь процесс загрузки.
* **Трассируемость:** сообщение ошибки указывает `config_id`, `type` и конкретное несоответствие.
* **Простота и скорость:** проверки выполняются за O(1), не используют сторонние библиотеки.
* **Поддержка будущих версий:** список допустимых типов централизован в `ConfigType(Enum)`.

### C-5 Допущения и ограничения

* Секция `meta` гарантированно соответствует схеме `meta_dto.py` (базовые поля, включая `config_id`, `version`, `pipeline_step`) — проверка формата и значений выполняется на более поздних этапах.
* Проверка `expected_version` ограничена синтаксисом: `1.2.3`, `1.x`, `1.2.x` (маски разрешены). Более сложные правила миграций здесь не обрабатываются.
* Проверка уникальности `config_id` по всем конфигам выполняется позже (на этапе итоговой сборки результатов).

### C-6 Критерии приёмки

* Конфиг, у которого есть `meta` и `profiles` с корректными типами, проходит sanity-check.
* Если отсутствует ключ `meta` или `profiles` → ошибка `SANITY_MISSING_KEY`.
* Если `meta.config_id` не совпадает с `config_id` из манифеста → ошибка `SANITY_CONFIG_ID_MISMATCH`.
* Если `meta.version` не соответствует `expected_version` → ошибка `SANITY_VERSION_MISMATCH`.
* Если `meta.pipeline_step` не входит в `ConfigType(Enum)` → ошибка `SANITY_UNKNOWN_TYPE`.

## D. `_ConfigUniversalJsonSchemaValidation`. Валидация по JSON Schema

### D-1. Цель класса

Подтвердить, что конфигурационный файл строго соответствует своей JSON Schema. Это гарантирует корректность структуры, типов данных и значений до перехода к дальнейшей нормализации и проекции в DTO.

### D-2. Библиотеки и технические подходы

* **`jsonschema` (Draft202012Validator)** — строгая проверка документа против соответствующей схемы.
* **Резолвер `$ref`** — для корректной загрузки вложенных ссылок (например, `./meta.schema.json`).
* **Fail-fast исключения** — немедленный останов при первой ошибке.

### D-3. Функциональные требования

1. Определить путь к схеме в зависимости от `ConfigEntry.type`.
   
   * Если схема отсутствует → немедленный fail-fast.

2. Провести валидацию JSON-объекта против схемы.

3. При обнаружении несоответствия → fail-fast с информацией о JSON Pointer, ожидаемом и фактическом значении.

4. Если ошибок нет → передать документ дальше без изменений.

### D-4. Нефункциональные требования

* **Fail-fast:** один сбой останавливает весь процесс загрузки.
* **Трассируемость:** фиксировать, какая схема применялась, и точку отказа.
* **Совместимость:** использовать только Draft 2020-12.
* **Детерминизм:** одна и та же схема и конфиг всегда дают одинаковый результат.

### D-5. Допущения и ограничения

* Схемы всегда доступны в проекте: `manifest/v1/*.schema.json` и `configs/v1/*.schema.json`.
* Используется только актуальная версия v1.
* Семантические проверки (например, `sheet_name_core_limit ≤ sheet_name_max_len`) выполняются не на этом этапе, а позже.

### D-6. Критерии приёмки

* Валидный конфиг проходит проверку без ошибок.
* При невалидном JSON (отсутствие ключа, неверный тип, лишние свойства) возникает ошибка `SCHEMA_VALIDATION_FAILED` с указанием причины.
* При отсутствии схемы возникает ошибка `SCHEMA_NOT_FOUND`.

### D-7. Перечень кодов ошибок

* `SCHEMA_NOT_FOUND` — схема для данного типа конфига отсутствует.
* `SCHEMA_VALIDATION_FAILED` — несоответствие содержимого конфигурации JSON Schema.

## F. `_ConfigActiveProfileSelector`. Обработка профилей

### F-1. Цель класса

Обеспечить выбор и нормализацию активных профилей в конфигурации, исходя из правил работы с `meta.active_profiles` и массива `profiles[]`.

### F-2. Библиотеки и технические подходы

* **Базовые операции Python (`dict`, `list`)** — проверка и фильтрация профилей.
* **Fail-fast исключения** — немедленный останов при нарушении правил.

### F-3. Функциональные требования

1. Если `active_profiles` пустой → выбрать первый элемент массива `profiles`.

2. Если `active_profiles` содержит значения → выбрать профили строго по их `profile_id` в указанном порядке.

3. Fail-fast, если:
   
   * `profile_id` из `active_profiles` отсутствует в `profiles`;
   * `active_profiles` содержит дублирующийся `profile_id`.

### F-4. Нефункциональные требования

* **Детерминизм:** одинаковый вход → одинаковый набор активных профилей, с сохранением порядка.
* **Fail-fast:** при несоответствии профилей загрузка останавливается.
* **Прозрачность:** сообщение об ошибке должно содержать `config_id`, `type` и проблемный `profile_id`.

### F-5. Допущения и ограничения

* Минимум один профиль в массиве `profiles` гарантирован JSON Schema.
* Список `active_profiles` всегда массив строк (гарантия JSON Schema).
* Дополнительная логика (например, семантическая проверка уникальности `profile_id` внутри массива) выполняется на других под-этапах.

### F-6. Критерии приёмки

* При пустом `active_profiles` выбран первый профиль.
* При непустом списке выбран ровно тот набор профилей, что указан в `active_profiles`, в правильном порядке.
* При ошибке формируется код и сообщение с указанием `profile_id`.

### F-7. Перечень кодов ошибок

* `PROFILE_NOT_FOUND` — `profile_id` из `active_profiles` отсутствует в `profiles`.
* `PROFILE_DUPLICATE` — `active_profiles` содержит дубликаты `profile_id`.
* `PROFILE_ARRAY_EMPTY` — массив `profiles` пуст (должен перехватываться на раннем этапе, но дублируется для надёжности).

## E. `_ConfigSemanticInvariantsByType`. Семантические инварианты

8. **meta**

## G. `_ConfigPlaceholderFilling`. Интерполяция плейсхолдеров

### G-1. Цель класса

Заменить плейсхолдеры вида `${env:VAR}` и `${secret:KEY}` в конфигурации на реальные значения. Этот шаг связывает конфиг с окружением и секретами, делая его готовым для проекции в DTO.

### G-2. Библиотеки и технические подходы

* **`os.environ`** — источник значений для `${env:VAR}`.
* **`streamlit.secrets` (`st.secrets`)** — источник значений для `${secret:KEY}`.
* **Рекурсивный обход словарей/списков** — поиск и подстановка строковых значений с плейсхолдерами.
* **Fail-fast исключения** — если ключ отсутствует в источнике.

### G-3. Функциональные требования

1. Найти все строки, содержащие `${env:VAR}` или `${secret:KEY}`.
2. Подставить значение из `os.environ` или `st.secrets`.
3. Fail-fast, если ключ отсутствует в источнике.
4. Запрещено логировать подставленные значения (особенно секреты).

### G-4 Нефункциональные требования

* **Безопасность:** секреты никогда не должны попадать в логи или ошибки.
* **Fail-fast:** отсутствие ключа останавливает загрузку.
* **Детерминизм:** одно и то же окружение и входные данные → один и тот же результат.
* **Прозрачность:** сообщение об ошибке указывает только имя отсутствующего ключа, без его значения.

### G-5. Допущения и ограничения

* Поддерживаются только два типа плейсхолдеров: `${env:...}` и `${secret:...}`.
* В текущем релизе **нет** альтернативных провайдеров секретов.
* Интерполяция выполняется только по строковым значениям.

### G-6. Критерии приёмки

* Все плейсхолдеры заменяются на реальные значения.
* Если значение отсутствует → ошибка fail-fast.
* В итоговом JSON плейсхолдеров не остаётся.

### G-7. Перечень кодов ошибок

* `INTERPOLATION_ENV_NOT_FOUND` — переменная окружения не найдена.
* `INTERPOLATION_SECRET_NOT_FOUND` — секрет не найден.

### K-5. Допущения и ограничения

### K-6. Критерии приёмки

* При ошибках формируется структурированная диагностика с JSON Pointer.
* DTO сохраняется в итоговую коллекцию без искажений.

### K-7. Перечень кодов ошибок

## R. `_ErrorFormatter`

### R-1. Цель класса

Обеспечить единый механизм формирования **структурированных ошибок** во всём модуле `ConfigLoader`. Класс преобразует исключения от `json`, `jsonschema`, Pydantic и внутренних fail-fast проверок в унифицированный формат с полями:
`code`, `message`, `config_id`, `type`, `profile_id?`, `json_pointer?`.
Это позволяет детерминированно диагностировать сбой и связать его с конкретным конфигом и профилем.

### R-2. Библиотеки и технические подходы

1. **`dataclasses` (stdlib)** — для определения структуры объекта ошибки.
2. **`traceback` / `sys.exc_info`** — для безопасного извлечения текста исключений.
3. **`jsonschema.ValidationError`** — для извлечения JSON Pointer.
4. **`pydantic.ValidationError`** — для извлечения путей до полей DTO.
5. **Внутренние исключения ConfigLoader** (`BusinessInvariantError` и др.) — конвертируются в структуру с кодом слоя (`SANITY_*`, `SEMANTIC_*`, `RESULT_*`).

### R-3. Функциональные требования

1. Принимать на вход произвольное исключение и контекст (`config_id`, `type`, `profile_id?`).
2. Определять класс ошибки и сопоставлять с кодом слоя (`IO_*`, `SCHEMA_*`, `DTO_*` и т.д.).
3. Извлекать сообщение ошибки (чёткое и воспроизводимое).
4. Если исключение содержит путь к проблемному полю (`ValidationError.path`, `pydantic.error_loc`), формировать `json_pointer`.
5. Возвращать объект-ошибку (dataclass или dict), готовый для сериализации.

### R-4. Нефункциональные требования

* **Детерминизм:** одинаковый вход (ошибка + контекст) всегда даёт одинаковый результат.
* **Прозрачность:** сообщение должно быть коротким, но информативным (без секретных значений).
* **Безопасность:** не раскрывать содержимое `st.secrets` и переменных окружения.
* **Расширяемость:** добавление новых кодов ошибок не требует переписывания логики преобразования.

### R-5. Допущения и ограничения

* Все ошибки приходят из фиксированных источников: `json`, `jsonschema`, Pydantic, внутренние классы.
* Ошибки уровня бизнес-логики потребителей **не входят** в область ответственности.
* `provenance` (путь, версия, активные профили) добавляется на уровне фасада `ConfigLoader`, а не в `_ErrorFormatter`.

### R-6. Критерии приёмки

1. Ошибка любого слоя модуля преобразуется в структуру `{code, message, config_id, type, profile_id?, json_pointer?}`.
2. Для ошибок `jsonschema` и Pydantic присутствует корректный `json_pointer`.
3. Для ошибок без явного указания поля `json_pointer` отсутствует.
4. Сообщение не содержит секретов.
5. В юнит-тестах проверяется покрытие всех групп кодов.

### R-7. Таблица кодов ошибок

| Код ошибки                       | Условие возникновения                              | Класс/этап, где возникает              |
| -------------------------------- | -------------------------------------------------- | -------------------------------------- |
| `IO_NOT_FOUND`                   | Файл манифеста/конфига отсутствует                 | `_ManifestReader`, `_ConfigReader`     |
