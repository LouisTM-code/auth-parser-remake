# Рекомендации по исправлению проблем статического аудита

### Введение

В ходе статического аудита исходного кода парсера были выявлены проблемы, связанные с инкапсуляцией, модульностью, избыточностью и расширяемостью.  
Цель данного документа — зафиксировать каждую проблему и предложить конкретные рекомендации по её исправлению.  

Документ служит промежуточной точкой (*момент А*):  

- он фиксирует **единый набор решений**, которые должны быть реализованы в коде;  
- обеспечивает **прозрачность аргументации**, чтобы в будущем понимать, почему принято то или иное решение;  
- создаёт **чек-лист для рефакторинга**, исключая противоречивые или устаревшие претензии.

### Формат описания проблем

Каждая проблема фиксируется в следующей структуре:

```markdown
### *Заголовок Проблема* (PR-N)
**Контекст:** (опционально — описание условий или предпосылок)  
**Текущая проблема:** (суть выявленного недостатка)  
**Рекомендация:** (конкретное действие по исправлению)  
**Аргументация:** (обоснование выбора и ожидаемый эффект)  
```

> **Структура документа** - Рекомендации сгруппированы **по областям (модулям)** проекта.

### `PriceNormalizer` (PR-1,PR-2,PR-3)

> Данный подход исправляет 1-3 проблемы. Больше информации и подробных действий в `Moments Updates/PR_NormalizerCompile.md`

**Контекст:**

Модуль `PriceNormalizer` содержит метод `_compile_actions`, который якобы должен готовить действия нормализации на старте. В реальности он возвращает пустой список, а реальная работа ведётся через строковые идентификаторы инструментов и `if/elif`.

**Текущая проблема:**

* `_compile_actions` не выполняет полезной работы → лишняя абстракция.
* Параллельно хранятся `_actions_by_field` и `_rules_by_field`, но первые всегда пустые.
* Инструменты вызываются по строковым `if/elif`, без настоящего плана шагов.

**Рекомендация:**

Заменить фиктивную «компиляцию» на реальную:

1. Все инструменты оформить как чистые функции `(value, ctx)`.
2. Поддерживать реестр `TOOL_REGISTRY: {имя → функция}`.
3. На этапе инициализации собирать для каждого поля список шагов (`pipeline`), который вызывает функции по порядку.
4. Использовать единый объект `NormalizationContext` для передачи параметров (например, `supplier_id`).

**Аргументация:**

* **Модульность:** добавление нового инструмента = новая функция + регистрация в реестре, без правок в `Normalizer`.
* **Гибкость:** правила (`tools`) остаются в конфиге `FieldSpec.normalize`; пайплайн формируется динамически.
* **Трассируемость:** каждый шаг можно логировать или тестировать отдельно; порядок и параметры фиксированы.
* **Чистота кода:** убираем пустой `_compile_actions`, дублирующий словарь `_actions_by_field`, и строковые `if/elif`.

### `ProductExtractor` (PR-4,PR-5,PR-6)

> Данный подход исправляет 4-6 проблемы. Больше информации и подробных действий в `Moments Updates/PR_ExtractorWithDI.md`

#### Жёсткая пятёрка полей и глобальные константы (PR-4/5)

**Контекст:** `ProductExtractor` строит `ProductRecord` через первые 5 `FIELD_SPECS`, а контейнеры и поля жёстко тянет из глобальных констант.
**Текущая проблема:** Добавление новых полей или поддержка другого сайта требует правок кода; экстрактор негибок и трудно тестируем.
**Рекомендация:** Перевести `ProductExtractor` на обход всех `field_specs` по именам полей, возвращать `dict[str, Any]` вместо фиксированного dataclass, а `field_specs`/`container_specs` передавать через DI (из JSON-профиля).
**Аргументация:** Это убирает зависимость от индексов и глобалей, позволяет расширять поля и менять профили сайтов без изменений кода. Код экстрактора становится универсальным и проще тестируется.

#### Смешение обязанностей нормализации (PR-6)

**Контекст:** В `ProductExtractor` встроена конверсия цен в `float`, хотя за нормализацию отвечает отдельный модуль.
**Текущая проблема:** Дублирование логики с `PriceNormalizer`, риск рассинхронизации и непредсказуемых значений.
**Рекомендация:** Убрать любые преобразования из экстрактора; возвращать только сырые значения. Все правила применять только в `PriceNormalizer` через реестр инструментов и `NormalizeRules`.
**Аргументация:** Централизация нормализации делает систему предсказуемой, трассируемой и модульной. Один модуль отвечает за извлечение, другой — за преобразование.

### `ParserPipeline` (PR-7,PR-8,PR-9,PR-10)

> Данный подход исправляет 7-10 проблемы. Больше информации и подробных действий в `Moments Updates/PR_PipelineTask.md`

#### Потеря `task_id` при парсинге (PR-7/10)

**Контекст:**  
`ProductExtractor.extract` принимает параметр `task_id`, а `ParseIssue` хранит это поле для привязки ошибки к конкретной странице (`PageTask.id`).

**Текущая проблема:**  
В `ParserPipeline` при вызове экстрактора всегда передаётся фиксированный `task_id=0`. В результате все диагностические сообщения теряют привязку к конкретной странице/URL, что делает отладку и мониторинг затруднительными.

**Рекомендация:**  
Формировать список `PageTask` для каждого входного URL (с уникальным id и нормализованным URL) и прокидывать `task.id` в экстрактор.

**Аргументация:**

* Сохраняется сквозная трассируемость: `PageTask.id → ParseIssue.task_id`.

* В логах и UI легко находить проблемы конкретной страницы.

* Решение согласуется с моделью данных и повышает тестируемость.

#### Потеря трассируемости проблем (PR-8)

**Текущая проблема:**  
Из-за фиксированного `task_id=0` невозможно понять, какой URL или страница вызвали ошибку.

**Рекомендация:**  
Использовать `task_id` из `PageTask` во всех диагностических записях и событиях `LogBus`.

**Аргументация:**

* Прямая связь «ошибка ↔ страница» в логах.

* Улучшение наблюдаемости и аналитики в UI.

#### Дублирование дедупликации URL (PR-9)

**Текущая проблема:**  
В `ParserPipeline` реализована своя `_dedupe_keep_order`, хотя в `core.utils_text` уже есть `normalize_and_dedupe_urls` с аналогичной логикой.

**Рекомендация:**  
Удалить приватный метод `_dedupe_keep_order`, использовать `normalize_and_dedupe_urls` из `utils_text`.

**Аргументация:**

* Один источник истины, отсутствие дублирования.

* Упрощение поддержки, меньше риска рассинхронизации логики.

### `SessionManager` (PR-11)

> Данный подход исправляет 11 проблему. Больше информации и подробных действий в `Moments Updates/PR_UniteSessionManager.md`

#### Дублирование логики ретраев в `SessionManager.get`/`post` (PR-11)

**Контекст:** В сетевом слое требуется унифицированная обработка ошибок и повторов запросов, конфигурируемая через JSON-профиль.  
**Текущая проблема:** Методы `get` и `post` содержат почти идентичный код для ретраев и обработки ошибок. Это ведёт к дублированию, риску рассинхронизации логики и усложнению тестирования.  
**Рекомендация:** Вынести общую логику в приватный метод `_request_with_retries`, использовать единую структуру `RetryPolicy`, загружаемую из JSON-профиля, и централизовать правила принятия решения о повторе (`_should_retry_status`, `_should_retry_exception`).  
**Аргументация:** Такой подход устраняет дублирование, обеспечивает модульность и гибкость (правки политики делаются в профиле, а не в коде), улучшает трассируемость (однообразные правила для всех методов) и упрощает тестирование.

### `PageFetcher` (PR-12)

> Данный подход исправляет 12 проблему. Больше информации и подробных действий в `Moments Updates/PR_PageFetcherLogic.md`

#### Ликвидация жёсткой привязки к `SHOWALL_*`  и другим операциям над url (PR-12)

**Контекст:**  
`PageFetcher` в текущей реализации автоматически добавляет параметры `SHOWALL_*` ко всем URL. Это унаследованная логика под один конкретный сайт.

**Текущая проблема:**  
Сетевой слой становится доменно-специфичным, теряет универсальность. При расширении на другие сайты придётся переписывать код `PageFetcher`, а не только менять настройки. Трассируемость и тестируемость ухудшены, так как непонятно, где именно и почему меняется URL.

**Рекомендация:**  
Вынести трансформацию URL в отдельный модуль `UrlTransformer`, управляемый JSON-профилем. `PageFetcher` получает на вход уже нормализованный список URL и отвечает только за сетевые запросы.

**Аргументация:**

* **Модульность:** `PageFetcher` отвечает только за HTTP, правила нормализации централизованы в одном месте.

* **Гибкость:** добавление или изменение правил выполняется через JSON без правки кода.

* **Трассируемость:** легко логировать цепочку «сырой URL → нормализованный URL».

* **Тестируемость:** тесты сетевого слоя не зависят от доменной логики; правила URL тестируются изолированно.

* **Расширяемость:** можно подключать разные профили для разных сайтов без изменения ядра пайплайна.

### `FormAuthAdapter` (PR-13,PR-14)

> Данный подход исправляет 13-14 проблемы. Больше информации и подробных действий в `Moments Updates/PR_FormAuthAdapterDI.md`

#### Проблема: Жёстко заданные параметры в `FormAuthAdapter` (PR-13)

**Контекст:**

* В текущем коде `FormAuthAdapter` и `AuthConfig` содержат дефолтное значение `login_url="https://cnc1.ru/auth/?login=yes"`.

* Дополнительно в классе присутствует `_BROWSER_EXTRAS` с фиксированными заголовками (`Referer: https://cnc1.ru/?login=yes`, `User-Agent: ...`).

* Эти значения автоматически применяются при каждом вызове, независимо от того, какой сайт реально используется.

**Текущая проблема:**

* Адаптер становится жёстко привязанным к одному домену и сценарию (cnc1.ru).

* Подключение нового сайта требует изменения кода, а не конфигурации.

* Заголовки нельзя управляемо менять в разных окружениях (тест/прод), что усложняет отладку.

**Рекомендация:**

* Удалить дефолтные значения `login_url` и «браузерные заголовки» из кода адаптера.

* Вынести все параметры (метод, URL, заголовки, мэппинг полей формы, дополнительные hidden-поля) во внешний JSON-профиль авторизации.

* В `runner.py` загружать JSON-профиль, создавать объект `FormAuthProfile` и передавать его в `FormAuthAdapter` через DI.

**Аргументация:**

* Конфигурация становится декларативной и версионируемой, можно поддерживать разные сайты без переписывания кода.

* Уменьшается связность: адаптер превращается в универсальный «исполнитель», а бизнес-логика задаётся профилем.

* Появляется возможность централизованного управления заголовками и их политикой (например, хранить User-Agent в одном месте).

* Упрощается тестирование: для разных сайтов можно подменять JSON-профиль без пересборки проекта.

#### Проблема: Вывод ошибок логина в stdout (PR-14)

**Контекст:**

* При провале авторизации адаптер выводит фрагмент ответа сервера через `print(...)`.

* После этого выбрасывается исключение `LoginFailedError`.

* Таким образом, информация об ошибке дублируется: часть в stdout, часть через исключение.

**Текущая проблема:**

* Логи засоряются посторонним выводом.

* `print(...)` обходит систему логирования `LogBus`, из-за чего события не попадают в UI и не могут фильтроваться.

* Риск утечки конфиденциальных данных (логин/пароль, текст ответа) в stdout.

**Рекомендация:**

* Заменить все `print(...)` внутри `FormAuthAdapter` на вызовы `LogBus.error(...)` или `LogBus.info(...)` с кодами событий (`AUTH_RESPONSE`, `ERR_LOGIN_FAILED`).

* Добавить маскирование чувствительных полей (например, `USER_LOGIN`, `USER_PASSWORD`).

* Логировать только краткий фрагмент ответа сервера (например, первые 200 символов) с явным ограничением.

**Аргументация:**

* Вся информация об авторизации централизованно проходит через `LogBus`, что позволяет её отображать в UI и хранить в едином формате.

* Маскирование исключает риск утечки логинов и паролей в текст логов.

* Поддерживается единый контракт ошибок: в случае сбоя в пайплайне выбрасывается `LoginFailedError`, а информация о событии остаётся доступной в логах и UI.

* Убирается несогласованность: теперь нет «двух каналов» сообщений (stdout и лог-шина).

### `UI-логирование` (PR-15)

#### UI-логирование без ограничения (PR-15)

**Контекст:**  
В `app.ui.interface` логи сохраняются в `st.session_state["log_lines"]` как список, который бесконечно растёт.

**Текущая проблема:**  
При длительной работе размер списка увеличивается без ограничений, что ведёт к постоянному росту потребления памяти.

**Рекомендация:**  
Заменить список на кольцевой буфер (`deque(maxlen=N)`), где N берётся из JSON-конфига (`ui.log.max_lines`).

**Аргументация:**  
Ограничиваем память, сохраняем только последние N сообщений. Поведение для пользователя не меняется, но исчезает риск утечки памяти.

### `LogBus`  (PR-16)

#### Дублирование API в LogBus (PR-16)

**Контекст:**  
В `LogBus` реализованы методы `drain_batch` и `drain_batch_nowait`, которые содержат почти идентичную логику.

**Текущая проблема:**  
Нарушение принципа DRY: две реализации нужно сопровождать параллельно, что увеличивает риск ошибок и усложняет тестирование.

**Рекомендация:**  
Оставить единый метод `drain_batch(max_items, wait=False, timeout_ms=None)`. Удалить `drain_batch_nowait`, заменить вызовы на новый метод с `wait=False`.

**Аргументация:**  
API становится чище и проще, один источник истины. Легко расширять поведение (таймауты, фильтры) без дублирования.
