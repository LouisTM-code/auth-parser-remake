# Цель обновления

Устранить две проблемы логирования без изменения бизнес‑логики парсингаю. Достичь - модульности, гибкой конфигурации через JSON, улучшения трассируемости/тестируемости и готовности к дальнейшему расширению.

## Проблемы (как есть)

15. **UI** (`app.ui.interface`): `st.session_state["log_lines"]` — неограниченный список. Визуально отображаются последние \~2000 строк, но сам список бесконечно растёт.
16. **LogBus** (`app.app_logging.logbus.LogBus`): две публичные функции выгрузки с дублирующейся логикой, что нарушает DRY и осложняет сопровождение.

## Область применения

* Модули: `app.ui.interface`, `app.app_logging.logbus`.
* Интеграция: косвенные правки точек вызова логов в UI; остальные подсистемы (pipeline, parsing, net) не затрагиваются.

## Новая концепция работы через JSON‑конфиг

Вводится секция `log` в общем проектном конфиге (версионируемом), которая определяет поведение шины и UI:

```json
{
  "schema_version": "1.0",
  "log": {
    "bus": {
      "max_queue_size": 2000
    },
    "ui": {
      "max_lines": 2000,
      "batch_pull": 200,
      "render_limit": 2000
    }
  }
}
```

**Пояснения:**

* `bus.max_queue_size` — верхняя граница для внутренней очереди `LogBus`.
* `ui.max_lines` — верхняя граница строк, хранимых в UI (кольцевой буфер).
* `ui.batch_pull` — сколько событий разово вытягивается из `LogBus` за тик UI.
* `ui.render_limit` — сколько последних строк максимум отдаём в рендер за один кадр (страховка для больших экранов/табов).

При отсутствии конфига — применяются безопасные дефолты.

## Пайплайн (требования и кодовые примеры) \[По порядку внедрения]

### 1) **Единый API в LogBus: `drain_batch(wait=...)`**

**Требование**

* Упростить API: оставить один публичный метод выгрузки `drain_batch`, который параметром `wait` управляет режимом ожидания. Удалить `drain_batch_nowait`.
* Сигнатура: `drain_batch(self, *, max_items: int | None = None, wait: bool = False, timeout_ms: int | None = None) -> list[LogEvent]`.

**Пример кода**

```python
# было
items = log_bus.drain_batch_nowait(max_items=200)

# стало (эквивалентный режим без ожидания)
items = log_bus.drain_batch(max_items=200, wait=False)

# в будущем (при необходимости ожидания с таймаутом)
items = log_bus.drain_batch(max_items=200, wait=True, timeout_ms=100)
```

**Мотивация**

* Один источник истины без дублирования логики, проще поддерживать и тестировать.
* Расширяемость: можно добавить таймаут/фильтрацию без размножения методов.

> Описание нового поведения: По умолчанию (`wait=False`) метод ведёт себя как прежний `nowait`: собирает доступные события, не блокируясь. `wait=True` зарезервирован на будущее (в текущей итерации необязателен для UI).

#### Изменения для каждого зависимого компонента от основного обновления

**Требование**

* В `app.ui.interface` заменить вызовы `drain_batch_nowait` на `drain_batch(wait=False)`.

**Пример кода**

```python
# было
events = log_bus.drain_batch_nowait(max_items=cfg.log.ui.batch_pull)

# стало
events = log_bus.drain_batch(max_items=cfg.log.ui.batch_pull, wait=False)
```

**Мотивация**

* Прямая адаптация к новому API, без изменения поведения UI.

### 2) **Bounded‑буфер в UI: кольцевой `deque(maxlen=N)`**

**Требование**

* Заменить `st.session_state["log_lines"]` с `list` на `collections.deque` с ограничением `maxlen = cfg.log.ui.max_lines`.
* Не хранить больше N строк в памяти — старые автоматически выталкиваются.

**Пример кода**

```python
from collections import deque

# инициализация (вместо списка)
if "log_lines" not in st.session_state or not isinstance(st.session_state["log_lines"], deque):
    # N берём из конфига, иначе дефолт
    st.session_state["log_lines"] = deque(maxlen=cfg.log.ui.max_lines or 2000)

# добавление строк
for ev in log_bus.drain_batch(max_items=cfg.log.ui.batch_pull, wait=False):
    line = f"{ev.ts} | {ev.level:<5} | {ev.code:<18} | {ev.msg}"
    st.session_state["log_lines"].append(line)

# рендер: можно напрямую, render_limit как страховка
lines = list(st.session_state["log_lines"])  # делаем список для slice
lines_to_show = lines[-(cfg.log.ui.render_limit or 2000):]
```

**Мотивация**

* Жёсткая верхняя граница памяти UI на логи, детерминированное поведение на длинных сессиях.

> Описание нового поведения: UI всегда хранит не более `N` последних строк логов; визуально ничего не меняется, но память не растёт бесконтрольно.

#### Изменения для каждого зависимого компонента от основного обновления

**Требование**

* Лёгкая адаптация `_render_logs`: использовать `render_limit` при формировании HTML; остальной код неизменен.

**Пример кода**

```python
lines = list(st.session_state["log_lines"])  # deque -> list
lines_to_show = lines[-(cfg.log.ui.render_limit or 2000):]
html = "<br/>".join(lines_to_show)
# дальше тот же markdown/скрипт авто‑скролла
```

**Мотивация**

* Никаких визуальных изменений для пользователя, только отказ от скрытого накопления памяти.

## Нефункциональные требования

* **Память**: UI удерживает не более `ui.max_lines` строк логов (O(N)). LogBus очередь — не более `bus.max_queue_size` событий.
* **Производительность**: операции добавления в deque — O(1). Выгрузка батчем — O(k), где `k ≤ batch_pull`.
* **Надёжность**: при недоступности конфига используются безопасные дефолты (2000/200/2000).
* **Совместимость**: требуется обновить вызовы `drain_batch_nowait` → `drain_batch(wait=False)`.
* **Конфигурируемость**: все параметры вынесены в JSON (секция `log`), версия определяется `schema_version`.
