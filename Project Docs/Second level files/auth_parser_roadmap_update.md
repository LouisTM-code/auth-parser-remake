# Roadmap обновления архитектуры и модулей Auth Parser

Документ фиксирует **последовательность и приоритеты** пошагового внедрения новой архитектуры и обновления существующих модулей. Цель — обеспечить модульность, гибкость, трассируемость и единый источник истины через конфиги JSON, сохранив производительность и предсказуемость.

---

## 1. Введение и цели обновления

**Цели:**
- Разделить обязанности: *извлечение ≠ нормализация ≠ сетевая логика ≠ авторизация ≠ логирование*.
- Перенести правила, константы и настройки в **версионируемый JSON‑конфиг**.
- Обеспечить **внедрение зависимостей (DI)**: модули получают всё необходимое через аргументы/параметры, а не глобальные импорты.
- Восстановить **сквозную трассировку**: ошибки и предупреждения привязываются к `task_id` и странице/URL.
- Минимизировать дублирование, устранить скрытые зависимости, обеспечить «один источник истины» для правил.
- Сохранять и улучшать производительность за счёт предкомпиляции правил и экономии аллокаций.

**Ограничения и исходные принципы:**
- Нулевые скрытые зависимости между доменными модулями (подключение данных только аргументами/конфигом).
- Единая модель ошибок верхнего уровня; отсутствие `print(...)` в пользу централизованной шины логов.
- Переиспользуемость: поддержка нескольких сайтов/профилей без изменения кода (только через JSON‑профили).

---

## 2. Требования к коду и его реализации

- **Версия Python:** 3.13.5.
- **Стандарты:** PEP8, полная аннотация типов, dataclass там, где это уместно; имена: *CamelCase* для классов, *snake_case* для функций/методов, **UPPER_CASE** для констант, имена файлов — *snake_case*.
- **Принципы ООП:** инкапсуляция, наследование (только при реальной полиморфной необходимости), полиморфизм, абстракция. Композиция предпочтительнее наследования.
- **Стремление к 0 зависимостям между модулями:**
  - Модули не «тянут» друг друга для данных; все параметры, правила, профили и стратегии передаются через аргументы, конструкторы или фабрики.
  - Запрещены скрытые синглтоны и глобальное состояние.
- **Подробное комментирование:**
  - У каждой функции/метода — чёткий docstring: назначение, входы, выходы, исключения, инварианты, сложность (при необходимости).
  - Обоснование выбранного алгоритма/структуры; указание на trade‑off’ы.
  - Явные пометки временных решений и TODO с критериями снятия.
- **Тестируемость:**
  - Юнит‑тесты на публичный API модулей; изоляция через DI и фикстуры.
  - Интеграционные тесты на ключевые сценарии пайплайна.
  - Контроль регрессий: snapshot/fixture‑данные в тестах, сравнение результатов.
- **Логирование:** только через LogBus/интерфейс UI; без `print`.
- **Производительность и память:** избегать лишних аллокаций, использовать предкомпиляции (регэкспы, правила нормализации), кольцевые буферы в UI.

## 3. Карта зависимостей и поток данных (целевое состояние)

```
URLs (raw)
  └─► UrlTransformer (профиль JSON: правила преобразований)
        └─► URLs (normalized)
              └─► SessionManager (унифицированные ретраи) + PageFetcher (без доменной логики)
                    └─► HTML pages
                          └─► ProductExtractor (DI: field_specs, container_specs)
                                └─► Raw records
                                      └─► Normalizer (реестр инструментов, предкомпиляция из JSON)
                                            └─► Normalized records
                                                  └─► Export (XLSX)

Side‑channels:
  * ParserPipeline оркестрирует стадии, присваивает PageTask/task_id, шлёт события в LogBus/UI.
  * Конфиг‑слой поставляет профили: auth, session/retry, url_rules, extract_specs, normalize_rules, ui.
```

## 4. Ключевые этапы обновления (приоритеты, стратегия, критерии приёмки)

> Каждый этап выполняется в отдельной ветке, с ревью, автотестами и релизной меткой. Параллель возможен там, где явно отмечено. На каждом этапе — миграционные примечания и обратная совместимость.

### Этап 1. Определение и документирование структуры и формата JSON‑конфига
**Цель:** единый источник истины для правил и настроек; возможность подключать новые сайты/профили без правки кода.

**Состав профиля (минимальный):**
- `meta`: `{ "version": "1.x.y", "site": "<идентификатор>", "updated_at": ISO8601 }`.
- `auth`: `{ "type": "form", "url": ..., "method": "POST", "headers": {...}, "form": {"USER_LOGIN": "${secrets.email}", ...} }`.
- `session`: `{ "timeouts": {...}, "retry_policy": {"max_retries": N, "backoff_base": 0.3, "statuses": [408, 429, 5xx], "exceptions": [...]}, "headers": {...} }`.
- `url_rules`: массив шагов трансформации (см. Этап 3): `add_query`, `ensure_scheme`, `dedupe_query`, `sort_query`, `replace_host`, и т. п.
- `extract_specs`: `container.selectors: [...]`, `fields: [{ name, selectors: [...], is_unique, normalize: [...] }]`.
- `normalize_rules`: описываются в составе `fields[].normalize.tools` (цепочки инструментов).
- `pipeline`: `{ "batch_size": 10, "concurrency": 24, "fetch_timeout_s": 25.0 }`.
- `ui`: `{ "log": { "max_lines": 5000, "poll_ms": 500 } }`.

**Стратегия:**
- Ввести JSON Schema **v1** для валидации; поддержать `meta.version` для будущих миграций.
- Прописать приоритеты переопределений: *по умолчанию* → *профиль сайта* → *переменные окружения/секреты*.

**Критерии приёмки:**
- Существуют: `profile.schema.json` и эталонный `profile.example.json`.
- Утилита валидации профиля возвращает OK на пример и выдаёт диагностические ошибки на некорректный профиль.
- Документация полей и допустимых значений присутствует в самом репозитории.

**Параллель:** возможно параллельно с Этапом 2.

---

### Этап 2. Создание инфраструктуры конфигурирования (без скрытых зависимостей)
**Цель:** централизованная загрузка/валидация/раздача профилей модулю, не создавая циклических импортов.

**Стратегия:**
- Ввести легковесный `ConfigLoader`:
  - `load(path) -> dict` (валидация по Schema, расширение переменных `${...}`).
  - Фабрики: `make_auth_adapter(cfg)`, `make_session(cfg)`, `make_url_transformer(cfg)`, `make_specs(cfg)` и т. п.
- Никаких глобальных синглтонов; все фабрики вызываются из точек входа (UI/runner).

**Критерии приёмки:**
- Юнит‑тесты на загрузчик и фабрики; отказоустойчивые сообщения об ошибках.
- Нулевая утечка зависимостей: ни один доменный модуль не импортирует `ConfigLoader`.

**Параллель:** возможно параллельно с Этапом 3 и частично 6.

---

### Этап 3. Реализовать новый модуль `UrlTransformer`
**Цель:** убрать доменную логику из сетевого слоя; централизовать преобразования URL по правилам из профиля.

**Стратегия:**
- Ввести интерфейс `UrlTransformer.transform(url) -> str` и, опционально, `transform_many(urls) -> list[str]`.
- Поддержать шаги: `add_query({key: value})`, `ensure_scheme("https")`, `dedupe_query()`, `sort_query()`, `replace_host(...)`, `strip_fragments()`.
- Прозрачность: вернуть, при необходимости, карту соответствия `orig → normalized`.

**Критерии приёмки:**
- PageFetcher **не** модифицирует URL; все изменения выполняет `UrlTransformer`.
- Юнит‑тесты на каждый шаг и их композиции; idempotency (`transform(transform(u)) == transform(u)`).

**Параллель:** да, с Этапом 7 (частично), так как PageFetcher будет упрощаться.

---

### Этап 4. Обновить `ProductExtractor` и переработать `core.models_and_specs`
**Цель:** сделать экстрактор универсальным и независимым от жёстких индексов и глобалей.

**Стратегия:**
- DI: передавать `field_specs` и `container_specs` из профиля в конструктор.
- Исключить жёсткие обращения к первым N полям; обход всех `field_specs` по именам.
- Возвращать сырой словарь/запись со значениями полей (без нормализации). Допускается внутренний тип‑алиас `Record`.
- В `models_and_specs` сохранить только DTO (минимально необходимое), позволив расширять набор полей профилем.

**Критерии приёмки:**
- Добавление нового поля в `extract_specs.fields` **не требует** правок кода.
- В тестах изменения верстки (альтернативные селекторы) покрываются вариантами `selectors`.
- Отсутствие любого бизнес‑преобразования в экстракторе (только извлечение/очистка текста).

**Параллель:** ограниченная — зависит от Этапа 1 (структура `extract_specs`).

---

### Этап 5. Обновить `Normalizer` (ранее `PriceNormalizer`)
**Цель:** заменить условные ветки инструментов на реестр и предкомпилированные пайплайны правил.

**Стратегия:**
- Ввести реестр инструментов `TOOL_REGISTRY: { name -> (value, ctx) -> value }`.
- На старте **компилировать** для каждого поля последовательность функций на базе `fields[].normalize.tools`.
- Поддержать контекст (`supplier_id` и др.). Удалить мёртвую `_compile_actions` и дублирующие структуры.
- Обеспечить чистоту и идемпотентность инструментов; «NA» пропускать без изменений.

**Критерии приёмки:**
- Добавление инструмента требует: 1) новую чистую функцию; 2) регистрацию в реестре; **без** правок основного класса.
- Нормализатор работает с **словарями записей**, не требует фиксированного `ProductRecord`.
- Бенчмарк на тестовом датасете показывает не хуже прежнего времени (±5%).

**Параллель:** частично с Этапом 4 (на уровне контрактов записей).

---

### Этап 6. Обновить `ParserPipeline`
**Цель:** оркестрировать новый поток: UrlTransformer → Fetch → Extract → Normalize → Export; восстановить `task_id` и убрать дублирование утилит.

**Стратегия:**
- Перед началом — нормализация и дедупликация входных URL **утилитой** (единый источник истины), затем `UrlTransformer`.
- На каждый URL формировать `PageTask {id, url, normalized_url}`; передавать `task_id` в экстрактор.
- Прогресс инкрементируется после обработки каждого URL независимо от исхода (OK/ошибка).
- Конфигурация батчей, таймаутов и параллелизма — из профиля.

**Критерии приёмки:**
- Логи партии агрегированы; при Stop выполняется частичный экспорт и корректная смена статусов UI.
- В ParseIssue/логах присутствует корректный `task_id` для каждой страницы.
- Внутренний дубликат утилиты дедупликации удалён.

**Параллель:** да, после Этапов 2–5 доступны интеграционные тесты.

---

### Этап 7. Обновить `SessionManager`, `PageFetcher`
**Цель:** устранить дублирование ретраев и убрать доменную логику из загрузчика страниц.

**Стратегия:**
- `SessionManager`: выделить приватный `_request_with_retries(...)`; параметризовать стратегию ретраев профилем.
- `PageFetcher`: никакой правки URL; только параллельные GET с семафором и сбор результатов.

**Критерии приёмки:**
- Единое место принятия решения «повторять/не повторять» по статусам/исключениям.
- Покрытие тестами таймаутов, сетевых ошибок и успешных сценариев с контролем количества попыток.

**Параллель:** возможно параллельно с Этапами 3 и 6.

---

### Этап 8. Обновить и внедрить логирование (UI + LogBus + адаптеры)
**Цель:** централизованное логирование событий и ошибок, ограничение потребления памяти UI.

**Стратегия:**
- В UI заменить список логов на кольцевой буфер `deque(maxlen=ui.log.max_lines)`.
- В коде авторизации и пайплайна — убрать `print`, использовать только LogBus.
- Маскирование чувствительных данных в логах; ограничение размера фрагментов ответов.

**Критерии приёмки:**
- На длительном прогонах потребление памяти UI стабильно.
- Все события отображаются через LogBus; присутствуют коды событий и `task_id`, где уместно.

**Параллель:** да, совместимо практически с любыми этапами после 1–2.

---

### Этап 9. Завершение и очистка
**Цель:** консолидация, удаление мёртвого кода, выравнивание документации и тестов.

**Стратегия:**
- Убрать неиспользуемые функции/дубли; выровнять docstring‑и и комментарии по новым контрактам.
- Обновить пользовательскую документацию (README/UI подсказки).
- Провести интеграционные прогон/профилирование; зафиксировать метрики.

**Критерии приёмки:**
- Линтеры и статический анализ без ошибок; тесты «зелёные».
- Профилирование без регрессий производительности/памяти.

## 6. Политики тестирования, релизов и контроля изменений

- **Ветки:** `feature/<stage>-<short-name>`; PR со ссылкой на критерии приёмки этапа.
- **Версионирование профиля:** `meta.version` (semver); изменения Schema сопровождаются миграторами или описанием шага.
- **CI:** линтер, тип‑чекер, unit+integration, проверка Schema и примеров.
- **Метрики релиза:**
  - Время полного прогона на эталонном наборе URL.
  - Количество `ParseIssue` до/после (не должно расти без причины).
  - Пиковая память UI и процесса парсинга.

---

## 7. Критерии «готовности к релизу» (Definition of Done)

- Все этапы 1–8 выполнены и прошли приёмку; 9 — завершён.
- Нет остаточных глобальных зависимостей; DI покрыт тестами.
- Профиль JSON и инструменты нормализации документированы.
- Сквозная трассировка по `task_id` подтверждена в логах и в отчётах тестов.
- Производительность не хуже исходной, либо улучшена; регрессы обоснованы.

---

## 8. Примечания по рискам и смягчающим мерам

- **Риск несовместимости профилей:** использовать Schema‑валидацию и миграционные гайды на каждом изменении.
- **Риск скрытых зависимостей:** аудит импортов и модульные тесты‑заглушки, создающие модули через фабрики.
- **Риск регресса производительности:** ранние бенчмарки на Этапах 4–6; предкомпиляция правил в нормализаторе.
- **Риск разрастания логов:** лимиты UI, фильтрация по уровням, агрегированные события партий.

### Итог

Настоящий roadmap задаёт путь к синхронному обновлению модульной архитектуры: конфиги → DI‑инфраструктура → URL‑трансформации → универсальный экстрактор → компилируемый нормализатор → оркестрация пайплайна → унифицированная сеть → централизованные логи → финальная уборка. Он обеспечивает согласованность решений, прозрачные критерии приёмки и повторяемость результатов.
