# Спецификация Event Hooks (черновик v0.1)

> Цель: зафиксировать подход к событиям/хукам для сетевого и парсерного слоёв с минимальными зависимостями между модулями. Документ **не привязан к текущей реализации** и служит базой для будущих доработок после закрытия 17 проблем.

---

## 1) Переформулировка задачи

Нужно ввести единый подход к **хукам событий** для модулей проекта (сеть, пайплайн, авторизация, парсер, нормализация), чтобы:
- подключать трассировку/логи/метрики **без жёстких зависимостей**;
- передавать хуки в компоненты как **необязательные коллбеки** (по умолчанию — «пустые»);
- масштабировать функциональность хуков **без изменений ядра** модулей.

Обязательное требование: **LogBus остаётся транспортом UI-логов** и не принимает на себя обязанности определения контрактов событий; он использует адаптер, реализующий интерфейсы хуков.

---

## 2) Дизайн‑цели и принципы

- **Нулевая жёсткая зависимость.** Ядро модулей (SessionManager/Extractor/ParserPipeline) не импортирует LogBus и не знает о транспортах.
- **DI/инверсия зависимостей.** Конкретные обработчики событий внедряются извне (через конструктор/сеттор).
- **Fail‑safe и неблокирующе.** Хуки не должны тормозить рабочий поток; ошибки хуков не должны падать в бизнес‑логику.
- **Единые контракты.** Интерфейсы событий единообразны, контекст — структурированный.
- **Минимальная точка расширения.** Добавление нового транспорта/метрик не требует правок модулей.

---

## 3) Границы ответственности модулей

- `app/core/event_hooks.py` — **контракты** (интерфейсы/протоколы) и базовые пустые реализации.
- `app/app_logging/logbus.py` — **транспорт UI‑логов** + **адаптер** `LogBusHooks`, реализующий контракты хуков и пересылающий события в LogBus.
- Остальные модули (сеть/пайплайн/парсер) — **потребители** интерфейсов; принимают хуки опционально (по умолчанию Null‑реализации).

> Если объём адаптеров/транспортов вырастет, допускается вынести их в `app/core/event_hooks_adapters.py`.

---

## 4) Публичные интерфейсы (черновик)

### 4.1. Общий контекст событий

```python
@dataclass(slots=True)
class EventContext:
    trace_id: str | None = None      # опциональный внешний трейс (OpenTelemetry/др.)
    task_id: int | None = None       # идентификатор страницы/задачи пайплайна
    supplier_id: int | None = None   # контекст профиля, если применимо
    extra: dict[str, Any] | None = None  # произвольные поля адаптеров
```

От контекста к событиям добавляются **специализированные** структуры (см. ниже) — это предотвращает «раздувание» одного класса.

### 4.2. Сетевые события (SessionHooks)

```python
class SessionHooks(Protocol):
    def attempt_start(self, ctx: EventContext, method: str, url: str, attempt: int, max_attempts: int) -> None: ...
    def attempt_success(self, ctx: EventContext, method: str, url: str, attempt: int, status: int, elapsed_ms: float) -> None: ...
    def attempt_error(self, ctx: EventContext, method: str, url: str, attempt: int, err_kind: str, err_msg: str) -> None: ...
    def retry_scheduled(self, ctx: EventContext, method: str, url: str, attempt: int, backoff_ms: float) -> None: ...
    def give_up(self, ctx: EventContext, method: str, url: str, attempts: int, last_err_kind: str, last_err_msg: str) -> None: ...
```

- `err_kind` — нормализованный код причины (например, `TIMEOUT`, `NETWORK`, `HTTP_5XX`).
- Все методы **должны быть неблокирующими** (адаптеры сами буферизуют/асинхронят при необходимости).

### 4.3. Хуки пайплайна (ParserHooks) — МVP‑набор

```python
class ParserHooks(Protocol):
    def fetch_start(self, ctx: EventContext, url: str) -> None: ...
    def fetch_done(self, ctx: EventContext, url: str, status: int, elapsed_ms: float) -> None: ...
    def extract_done(self, ctx: EventContext, count: int, issues: int) -> None: ...
    def normalize_done(self, ctx: EventContext, count: int) -> None: ...
    def export_done(self, ctx: EventContext, xlsx_path: str) -> None: ...
```

> Набор минимален; расширяем по мере потребностей. Допускается объединение с `SessionHooks` в единый адаптер, если это удобнее.

### 4.4. Пустые реализации (Null)

```python
class NullSessionHooks(SessionHooks):
    def attempt_start(self, *a, **kw): pass
    def attempt_success(self, *a, **kw): pass
    def attempt_error(self, *a, **kw): pass
    def retry_scheduled(self, *a, **kw): pass
    def give_up(self, *a, **kw): pass

class NullParserHooks(ParserHooks):
    def fetch_start(self, *a, **kw): pass
    def fetch_done(self, *a, **kw): pass
    def extract_done(self, *a, **kw): pass
    def normalize_done(self, *a, **kw): pass
    def export_done(self, *a, **kw): pass
```

### 4.5. Адаптер под LogBus

```python
class LogBusHooks(SessionHooks, ParserHooks):
    def __init__(self, logbus: LogBus, *, sampling: float = 1.0) -> None: ...  # sampling ∈ (0..1]
    # методы интерфейсов пересылают события в LogBus с кодами/контекстом
```

- Адаптер может применять **семплирование**, агрегацию батчей и маппинг кодов.
- Важно: **исключения из адаптера не пробрасываются** наружу (fail‑safe).

## 5) DI и точка подключения

- Компоненты принимают хуки через конструктор, параметр опционален:

```python
class SessionManager:
    def __init__(self, hooks: SessionHooks | None = None, ...):
        self._hooks = hooks or NullSessionHooks()
```

- Пайплайн собирает адаптеры и **вкручивает** их в компоненты (композиция сверху вниз). Нет импортов LogBus из модулей сети/парсера.

- Допускается «мультикаст» через простую обёртку `MultiHooks` (фан-аут на несколько адаптеров), если понадобится объединить UI‑логи и метрики.

---

## 6) Конфигурация (на будущее)

- Глобальный JSON‑профиль проекта может содержать раздел `hooks`:
  - вкл/выкл отдельных событий;
  - семплирование;
  - уровни серьёзности/фильтрация.
- Контракты хуков **стабильны**, включение/отключение управляется конфигом без правок кода модулей.

---

## 7) Поведение, производительность, отказоустойчивость

- Хук‑методы обязаны быть **быстрыми**; тяжёлые операции (I/O, сериализация, агрегация) — в адаптере с буферизацией/асинхронностью.
- Любая ошибка в хуке **проглатывается** и логируется адаптером как внутренняя (не влияет на бизнес‑поток).
- Допускается **декорирование** хуков для измерения времени/количества вызовов, если это не влияет на горячий путь.

---

## 8) Версионирование и совместимость

- Интерфейсы получают префикс **v1** на уровне документа/контрактов; при изменениях — вводить v2 рядом, не ломая v1.
- Изменения аргументов методов — только **добавления** с дефолтами; удаление/переименование — через новый интерфейс.

---

## 9) Тестируемость

- Юнит‑тесты компонентов используют `Null*Hooks` по умолчанию.
- Для проверки трассировки применяются **тестовые адаптеры** (накапливают события в список/очередь) и утверждают порядок/содержимое.
- Интеграционные тесты подключают `LogBusHooks` и проверяют сквозную доставку событий в UI.

---

## 10) План интеграции (минимально‑инвазивный)

1. Ввести `event_hooks.py` с интерфейсами и Null‑реализациями.
2. Добавить поддержку `hooks` в **SessionManager** (только DI‑вставка + вызовы на ключевых точках ретраев).
3. Реализовать `LogBusHooks` в `logbus.py` (минимальный маппинг событий → UI‑коды).
4. Подключить адаптер в пайплайне (создание и передача в SessionManager).
5. После стабилизации кода:
   - по необходимости расширить `ParserHooks` и подключить их в экстрактор/нормализатор/пайплайн;
   - рассмотреть `MultiHooks` и/или экспорт в метрики.

---

## 11) Риски и меры

- **Разрастание контрактов.** → Жёсткое правило: добавлять события только по факту потребности, фиксируя их в этом документе.
- **Перегрузка логами.** → Семплирование/фильтрация на стороне адаптера.
- **Скрытые зависимости.** → Компоненты знают только интерфейс; адаптеры не импортируются в модули ядра.
- **Сложность отладки.** → Простой тестовый адаптер и метки `trace_id`/`task_id` в EventContext.

## 13) Критерии приёмки (MVP)

- Компоненты принимают хуки как опциональные аргументы; при их отсутствии поведение неизменно.
- Включение `LogBusHooks` приводит к появлению структурированных UI‑событий без деградации производительности.
- Сбои внутри адаптера не влияют на ход бизнес‑операций.
- Документация (этот файл) отражает фактический набор событий и аргументов.

## 14) Открытые вопросы

- Нужно ли объединять `SessionHooks` и `ParserHooks` в один интерфейс для простоты внедрения?
- Нужны ли нам async‑хуки (например, `async def attempt_start`)? Пока считаем, что адаптеры сами решают вопрос асинхронности внутри.
- Требуется ли унификация кодов ошибок/событий на уровне контракта (список enum), или оставим свободу адаптерам?
