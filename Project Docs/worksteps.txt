<Этап 1. Чтение манифеста и Валидация по JSON Schema>
Прочитать и загрузить JSON-манифест конфигураций (v1), чтобы на его основе `ConfigLoader` мог знать какие типы конфигов доступны, какие версии и id ожидать и их пути.
На входе в этот этап нам необходимо только путь к манифесту
На выходе DTO `ConfigmanifestV1`, состоящий из `[manifest_meta: ManifestMeta(id, version, created_at, description, tags)]` и `[configs: список ConfigEntry (type, config_id, path, expected_version)]`. За это отвечает `manifest_dto.py`. (См. JsonSchemaSpec_2025-09-04.md)
Пошаговая логика действия этого этапа:
1. Fail-test на наличие файла по указанному пути;
2. Чтение содержимого;
3. Валидация манифеста по `manifest.schema.json`, и гарантия, что поле `configs` не пустое;
4. Заполнение всех DTO согласно `manifest_dto.py` из манифеста;
5. Fail-fast на:
* Наличие всех необходимых `type` конфигов;
* Уникальность `config_id`.
6. Готовые dataclass: `ConfigEntry`; `ManifestMeta`; `ConfigmanifestV1`.
</Этап 1. Чтение манифеста и Валидация по JSON Schema>

<Этап 2. Основной цикл по конфигам>
Каждый конфиг проходит сквозную обработку изолированно. Ошибка в одном конфиге приводит к немедленному fail-fast останову загрузки без попытки обработать остальные.
На входе в этот этап: DTO `ConfigmanifestV1` с массивом `configs: list[ConfigEntry]` берём по 1 `ConfigEntry`, где:
* type - class ConfigType(Enum);
* config_id - ункальный id конфига;
* path - путь относительно корня проекта `auth-parser-remake`;
* expected_version - semver.
Важно учитывать, что секция meta в конфигах одинаковая, поэтому эта секция вынесена в отдельную JsonSchema и `meta_dto.py`. 

<Под- этап 2.1. Разрешение пути и чтение>
Пошаговая логика под-этапа:
1. Разрешить path и прочесть json конфиг.
2. Прочитать файл, десериализовать.
Fail-fast: файл отсутствует/недоступен; невалидный JSON; пустой документ/не объект.
</Под- этап 2.1. Разрешение пути и чтение>

<Под- этап 2.2. Sanity-check>
Минимальные структурные проверки перед тяжёлой валидацией по JSON Schema и построением DTO. Обеспечить Fail-fast, чёткий код ошибки.
Проверки проводимые на под-этапе:
* Наличие ключей `meta` и `profiles` и соответствие типов;
* Соответствие `config_id` и `expected_version` из манифеста со значениями в обрабатываемом конфиге;
* `Type` из конфига существует в `class ConfigType(Enum)`.
</Под- этап 2.2. Sanity-check>

<Под-этап 2.3. Валидация по JSON Schema>
Обеспечить строгую проверку структуры и типов конфигурационного файла по его целевой JSON Schema.
На этом под-этапе есть:
* ConfigEntry
* JSON-объект конфига, прошедший Sanity-check.
Напоминаю, что эти параметры лежат в секции meta, которая вынесена в отдельную JsonSchema и `meta_dto.py`.
Пошаговая логика под-этапа:
1. Получаем путь к JSON Schema для соответствующего `Type`.
Fail-fast: если схема не найдена.
2. Запускаем валидацию через библиотеку `jsonschema` (Draft202012Validator, validate). Ловим Fail-fast в случае появления.
3. Подтверждение, что конфиг корректен относительно схемы.
</Под-этап 2.3. Валидация по JSON Schema>

<Под-этап 2.4. Обработка профилей>
Обеспечить корректный и детерминированный выбор активных профилей.
Это связывает два уровня:
* `active_profiles` из секции meta;
* массив `profiles[]` (набор вариантов внутри конкретного конфига).
Правило активации:
* Если `active_profiles` пустой - выбрать первый элемент массива `profiles`;
* Если список не пустой - выбрать строго те профили, чьи `profile_id` перечислены в `active_profiles`, сохранив порядок.
Fail-fast: `profile_id` из `active_profiles` отсутствует в массиве `profiles`; дублирующийся `profile_id`.
</Под-этап 2.4. Нормализация выбора профилей>

<Под-этап 2.5. Семантические инварианты>
На оснвоании `JsonSchemaSpec_2025-09-04.md` полный перечень семантических инвариантов разбитый по `Type`:
1. `auth`:
* Если `auth_type = "form"` - проверка наличия `request.method`, `request.endpoint` и `form_fields` не пустой;
* Если `csrf.enabled = true` - проверка наличия `source_url`, `token_selector` и `token_field_name`;
* `auth_type = "api_token"` и `api_token.enabled = true` - проверка наличия `token_header` и `token_value`;
* Для `success_checks[]` - должны иметь `params` (проверка содержимого лежит в модуле потребителе).
2. `export`:
* Проверка логики - `sheet_name_core_limit` ≤ `sheet_name_max_len` ≤ 31;
* Поддержка плейсхолдеров в `filename_pattern` лежит в модуле потребителе.
3. `logging`:
* Семантическая проверка: `ui.level` содержит значения `events.levels`.
4. `network`:
* проверка логики: `rate_limit.burst_size` ≥ `requests_per_second`;
* проверка логики: `retry_policy.timeout_budget_s` должен покрывать сумму задержек ретраев с учётом `max_attempts`, `initial_delay_s`, `backoff_multiplier`, `max_delay_s`;
* Если задан `session.request_timeout_s` - согласован с `retry_policy.timeout_budget_s` (не меньше и не конфликтовать).
5. `pipeline`
* Проверки отсутствуют.
6. `site`:
* Если `value_selector.extract = "attr"` - поле `attr` обязательно и не null / пустое;
* `page_container_selector` - не null / пустое;
* `item_containers` и `fields` - хотя схема допускает [] по умолчанию, но в текущем релизе эти поля не должны быть пустыми;
* Проверка уникальности `container_id` в пределах профиля и `field.name` в пределах контейнера.
7. `url`:
* Проверки отсутствуют. `condition.path_regex` проверяет модуль потребитель.
8. `meta`:
* На этом под-этапе проверки отсутствуют, их совершили на Sanity-check.
Fail-fast: нарушение любого инварианта.
</Под-этап 2.5. Семантические инварианты>

<2.7. Пред-DTO нормализация>
Конфиг уже прошёл Sanity-check; JSON Schema проверку (draft-2020-12); Семантические инварианты; Интерполяция плейсхолдеров. Но перед тем как строить Python DTO, привести данные к форме, с которой DTO-классы справятся. Нормализации, которые должны быть повторяемые и однозначные:
* Применение Default-значения (только те, что гарантированы схемой).
* DTO используют `Enum`. Канонизация enum/значений (например, регистр/вид).
Что делать нельзя: 
* Компиляцию regex, нормализацию URL, проверку форматов. Это зона потребителей.
* Вмешиваться в бизнес-логику.
* Генерировать значения «по умолчанию» за пределами того, что разрешает схема.
Если будут появляться ошибки при трансофрмации в DTO этот слой должен быть достаточно гибкий, чтобы обеспечить легкое расширение правил.

<2.8. Проекция в DTO>
Преобразовать подготовленный `dict` (конфиг + выбранные профили) в строго типизированный DTO-класс (`*_dto.py`).
Используется `Pydantic v2 TypeAdapter`:
* Создавать `TypeAdapter(TargetDTOClass)` для каждого DTO.
* Вызывать `validate_python(data)` для проекции, без создания `BaseModel.`
Центр приёма ошибок проекции:
* Перехватывать: несоответствие enum, типовой конфликт (int→float), null вместо коллекции, отсутствующий обязательный ключ, неожиданное поле.
* pointer (JSON Pointer до проблемного узла), `config_id`, `type`, `profile_id` (если применимо); - Сообщение должно быть конкретным и воспроизводимым: чтобы сразу ясно, что можно безопасно перенести в 2.7.
* Существование DTO-моделей `*_dto.py` для каждого конфига. * Напоминаю, что эти параметры лежат в секции meta, которая вынесена в отдельную JsonSchema и `meta_dto.py`.
Результат DTO сохраняется в итоговую структуру (если нет ошибок).
* Структура: {code, message, config_id, type, profile_id?, json_pointer}. Это упростит дальнейший лог.
</2.8. Проекция в DTO>

Мы будем реализовывать модуль `config_loader.py`. Но не сразу весь модуль - one-shot отмена. А постепенно - с комментариями согласно правилам и тестированием.
Сейчас модуля вовсе не существует. Поэтому начнём реализацию первого внутреннего класса `_ManifestReader` (только этот класс, после тестирования и *подгонки* - то можно думать о других классах).
<Требования>
## A. `_ManifestReader`

### A-1. Цель класса

* **(Вызов):** Получить путь к манифесту, с которого начинается работа загрузчика конфигураций. Этот шаг фиксирует точку входа без уточнения финального формата входа/выхода (может измениться при интеграции с `PipelineLauncher`).
* **(Чтение манифеста и валидация):** Прочитать JSON-файл манифеста, проверить его корректность по `manifest.schema.json`, гарантировать, что список `configs` не пуст, и построить DTO `ConfigManifestV1` с вложенными `ManifestMeta` и `ConfigEntry`. Дополнительно выполнить fail-fast проверки: обязательные типы конфигов присутствуют и `config_id` уникальны.

### A-2. Библиотеки и технические подходы

1. **`pathlib` (stdlib)** – для безопасной работы с путями и проверки наличия файла.
2. **`json` (stdlib)** – десериализация содержимого манифеста.
3. **`jsonschema` (внешняя)** – валидация против схемы `manifest.schema.json` (Draft 2020-12).
4. **DTO-модуль `manifest_dto.py`** – строгая проекция данных в dataclass-структуры `ConfigManifestV1`, `ManifestMeta`, `ConfigEntry`.
5. **Fail-fast проверки** – ручные проверки бизнес-правил, которые не покрыты JSON Schema: наличие всех обязательных типов (`pipeline`, `network`, `site`, `url`, `auth`, `logging`, `export`) и уникальность `config_id`.

### A-3. Функциональные требования

1. Проверить, что файл существует и доступен для чтения (иначе `FileNotFoundError`).
2. Загрузить JSON и проверить корректность синтаксиса (`json.JSONDecodeError` → fail-fast).
3. Провалидировать содержимое по `manifest.schema.json`.
4. Убедиться, что `configs` не пустой массив.
5. Заполнить DTO `ConfigManifestV1` из данных манифеста.
6. Проверить бизнес-инварианты:
   * все необходимые `type` представлены хотя бы один раз;
   * `config_id` уникальны во всём списке.

### A-4. Нефункциональные требования

* **Fail-fast:** ошибка любого шага прерывает загрузку немедленно, исключение должно быть информативным (`code`, `message`, `config_id`, `type`, `profile_id?`, `json_pointer`).
* **Детерминизм:** одинаковый входной файл → одинаковый результат DTO.
* **Трассируемость:** при ошибке валидации сообщать JSON Pointer до проблемного узла.
* **Изолированность:** модуль не зависит от `PipelineLauncher` и других модулей пайплайна.
* **Расширяемость:** поддержка новых версий манифеста достигается добавлением схемы и DTO, без изменения ядра.

### A-5. Допущения и ограничения

* Поддерживается только версия `manifest.schema.json` v1.
* Кеширование результатов чтения и валидации **не используется** в текущем релизе.
* Пути внутри манифеста трактуются как относительные к корню проекта или абсолютные.
* Проверка корректности формата `expected_version` (SemVer) выполняется на уровне схемы, а интерпретация версий и миграций **не входит** в `_ManifestReader`.
</Требования>
